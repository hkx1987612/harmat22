# 2026-11-09 - Connected Android CRM Read Client

## Approved Scope

User requested an Android CRM application for convenient viewing and fingerprint
sign-in. Implemented a new `apps/crm-android/:mobile` module, not a replacement of
the existing offline `:app` or older maintenance application. Public label:
Harmat CRM; application ID `hu.harmat22.crm.mobile`; test version `1.0.0-test`.

There is no live deployment, database migration, new API, role change or account
creation. Existing WordPress/CRM PHP, quote generation, appointment processing,
inventory records, customer data, website content and advertising remain intact.
No real CRM form submission or real company login was performed for this build.

## Data And Authentication

- Native overview/daily traffic, enquiry list, client files, sales deals and
  inventory read the existing authenticated `/sales/` rendering using jsoup.
  The existing server's account/object permission checks remain authoritative.
- Native requests are fixed HTTPS GETs for five allowlisted views. No arbitrary
  URL, redirects, export, customer download, business POST or edit/delete action.
  Changing `sales_lang` uses the portal's existing language-preference behavior.
- The isolated WebView handles the original account login only. JavaScript,
  JS bridges, third-party requests/cookies, file/content access and mixed content
  are disabled. SSL failures stop, not bypass. Passwords never enter native code.
- After receiving an auth cookie, the WebView is removed/destroyed and its local
  cookies/storage/cache cleared; the native reader verifies an authorized CRM
  page before displaying records or offering biometric session saving.
- This is not a new server read-only role. The same account retains its original
  website permissions. Its credentials must be entered by the user; no browser
  profile/cookie extraction, account impersonation or authentication bypass.
- Unknown HTML fails visibly without silently showing stale/demo/zero records.
  This adapter is coupled to the current CRM HTML and can require an app update
  after a portal redesign; it is not represented as a versioned API contract.

## Device Security

- Optional AES256/GCM session encryption uses Android Keystore, biometric-only
  per-operation authentication and the system BiometricPrompt CryptoObject.
  Native storage contains ciphertext and IV, not a saved password/auth cookie.
- New biometric enrollment/key invalidation or an expired/revoked server session
  requires normal account login again; a fingerprint cannot bypass server access.
- Leaving the foreground, screen-off or manual lock clears displayed records and
  decrypted cookie references, cancels pending reads and gates stale callbacks.
  The app re-fetches after unlock; it does not persist customer snapshots.
- Production windows/dialogs use FLAG_SECURE; no cloud backup/device transfer,
  analytics SDK, background polling, contacts, microphone, camera, location or
  external-storage permission. The temporary login WebView may internally write
  cookies in its private sandbox before cleanup; no forensic no-write claim.
- Signing uses a private RSA3072 identity in LOCALAPPDATA/HarmatCRM/Signing with
  a Windows-DPAPI protected password. Preserve the private key for updates; never
  commit/upload it, passwords, APKs, fixtures, screenshots or customer/session data.
- Debug `.qa` fixture mode is a separate package and only works in debug builds.
  Release is non-debuggable, has no fixture assets, ignores the demo intent and
  includes the pinned jsoup dependency's MIT notice. Existing icon is unchanged.

## Delivery And Recovery

Build with JDK17, Gradle8.10.2, AGP8.7.3, SDK35 and jsoup1.18.3. Minimum API28
(Android9); emulator evidence is API35, not certification of every physical phone.
`BuildMobile.ps1` signs, verifies signature/metadata and rejects fixture leakage.
The Windows process-local JDK unix-domain socket workaround changes no firewall.

The installable APK and private evidence remain in ignored
`outputs/2026-11-09-crm-android/`. No Play Store publishing, purchase or new service.
First real company login, role-limited records and the user's phone fingerprint
remain physical-device acceptance steps; synthetic tests cannot certify them.

Rollback requires only uninstalling this new application/local session. No site
database restore is appropriate; it could overwrite newer sales activity. The
old browser CRM and existing Android preview modules remain available unchanged.
