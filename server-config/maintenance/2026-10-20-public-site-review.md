## 第一批：先核实，再分开实施

### 0. 最高优先级：统一详情摘要的销售面积显示来源

随后逐套比对了全部 124 套公开房源。每页都成功读到“销售面积”字段：49 页与官网统一公开接口不完全相同，其中 29 页差 0.01–0.02 m²，应先核对舍入；另外 20 页差距超过 0.1 m²，值得优先人工核实。

例如 A4-F-L1 首页/统一接口/预约弹窗为销售面积 60.10 m²，但详情摘要将 57.05 m² 标为“销售面积”；A3-F-L3 为 47.39 对 43.74；A4-3-L1 为 111.57 对 111.07。这里比较的是同一销售面积标签，不是把明确标为室内面积的字段误判为错误。不是这次六套展示更改了房源数据，而是既有展示层使用不同计算/取值口径。

建议先核实这些原始户型及销售口径，再让详情摘要读取同一现有公共数据源；同时准确区分室内面积、室外面积、销售面积及单价分母。只修展示取值/标签，不批量覆盖物业元数据、不重新计算合同价格、不修改报价单或预约处理器。必须另行确认后才实施。

明显差异涉及：A1-F-L2/L3/L5/L7；A2-F-L1/L2/L3/L5/L7；A3-F-L1/L2/L3/L5/L7；A4-F-L1/L2/L3/L5/L7；A4-3-L1。当前六套中 A3-F-L3、A4-F-L1 的首页使用统一源，详情原摘要仍待修正。源头核实与展示一致性应排在 SEO 美化之前。

### 1. 让 sitemap 反映真正的内容更新时间

事实：首页 lastmod 仍为 2026-07-01；项目页为 2026-04-01；关于我们为 2026-07-29；施工日志为 2026-10-03。这些日期没有反映近期已上线的重大内容更新。视频 sitemap 仍仅列首页主宣传片。

建议：以经过核对的内容发布记录驱动 lastmod；不把每次访问或抓取时间伪装成更新时间。给后续新增的独立施工视频页加入准确的视频索引。只改公开索引输出，不改原页面 URL、客户数据或表单。

验收：XML 合法、无重复 URL、仅 canonical URL、日期可追溯；原页面标题/canonical/表单完全一致。Google 说明 lastmod 应反映真实的重大更新，且提交 sitemap 不保证收录：[Google sitemap 文档](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)。

### 2. 降低主视频和前端资源的开销，保留目前的观感

事实：当前主视频 HEAD 返回 200，大小 39,504,516 字节，支持字节范围请求及一年缓存。它不等于首次打开就下载完整 39.5 MB。首页 HTML 引用了 44 个外部脚本和 35 个样式表；这是标签数量，不是实际串行阻塞请求数，也不能直接换算成加载时间。

建议：保留电脑/电视高清、全宽完整画面和用户确认的循环播放；另外制作同内容的移动端轻量版本及清晰首帧。先逐项记录哪些脚本在实际页面被使用，再按页面延后加载 3D、图库等非首屏模块。不能直接批量停用 Elementor、主题脚本或表单依赖。

验收：记录改动前后真实加载字节和首帧时间；正常/慢网分别测手机与电脑，检查中匈切换、3D、视频循环、报价弹窗、日期时间选择。电视效果仍须实际设备确认，不以桌面模拟代替。

### 3. 检查图片占位及缩略图尺寸

事实：画廊的 53 个 img、选房页的 249 个 img 没有 HTML width/height；后者包含不同展示容器的图片节点，不代表 249 张独立图片全部立即下载。CSS 可能已经预留比例，因此不能仅凭缺少属性就认定发生布局跳动。

实际桌面浏览器抽查中，选房页卡片图像已有 220px 的显示高度，1280px 下未测得横向溢出。这一项应先确认现有 CSS 占位是否足够，而不是机械给所有图片套统一比例。

建议：先实测是否已有 aspect-ratio/稳定容器；有问题的模块补准确尺寸，卡片先用适合显示大小的缩略图，点开保留原始清晰图。首屏关键图不盲目懒加载，其余按需加载。

验收：筛选、图片加载、中匈切换时卡片不跳位，手机无横向溢出，灯箱及户型图仍可放大。参考：[web.dev 布局稳定性指导](https://web.dev/articles/optimize-cls)。

## 第二批：内容与搜索增长

### 4. 重点施工合辑建立独立观看页

事实：当前施工内容集中在日志页与日期锚点，已有结构化数据，但 sitemap 只有主宣传视频。

建议：精选有信息量的月度/阶段合辑，而非给每个重复短片都造页面。每条重点合辑有独立 URL、真实拍摄日期、对应楼栋、视频、字幕文字摘要和当期施工说明；首页仍只展示最新一条。未知进度比例不能猜写。

独立观看页需要让视频成为主要内容，播放器可被搜索引擎发现；不能只依赖点击后注入或 URL 锚点。施工总览仍可保留轻量按需播放，索引策略与观看页分开设计。视频 sitemap/VideoObject 要对应同一真实媒体和封面，不保证视频搜索曝光：[Google 视频 SEO 指导](https://developers.google.com/search/docs/appearance/video)。

### 5. 中文 SEO 与中文切换是两件事

事实：本次 145 页都以匈牙利语 URL 为 canonical，没有语言替代链接；现有中文切换改善使用体验，但没有独立的中文索引入口。

建议：若确实需要中文自然搜索获客，第二阶段先做 `/zh/` 首页、项目介绍、选房说明和联系页，使用内部翻译与独立标题/描述，再加中匈互相对应的 hreflang。逐步扩展房源，不一次复制全站。共享同一房源源头，不复制报价或预约处理器。

这不是要求接外部翻译服务。Google 对多语言推荐各语言使用不同 URL，而不是仅靠同 URL 动态切换：[Google 多语言网站指导](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)。

### 6. 用购房问题组织内容，而不是继续加长首页

建议：围绕“Budapest X. kerület új építésű lakás”“Kőbánya 新房”“带室外空间/两房三房”等真实需求，在已有项目、周边、融资和选房页补简短、可核实的信息。交通方式、生活配套、技术规格分别给出处和适用范围，不捏造距离/费用。保留首页简洁；详情页承接深入阅读。

面积要注明室内面积与销售面积的区别。例如 A1-F-L1 的 SEO 摘要为 57.05 m²，公开接口销售面积为 60.10 m²；两者不应擅自改成同一数字，建议摘要补清楚面积类型，必要时与户型图核实。这里只是表达清晰度建议，不修改面积、价格或报价单。

## 第三批：持续可靠性与维护

- 建议对公开页面、媒体 200/206、选房数据/详情链接和表单纯校验建立回归检查；真实预约通知链路的定期测试需单独授权，不能每天制造测试客户。
- 3D 后续若发生加载失败，保留清晰静态图和可直接进入楼栋/户型的替代入口。失败不是无限旋转等待；不要在没有证据时重新更换当前引擎。
- 页面和内容输出目前分布在多层 MU 兼容模块中。以后按“单模块、单所有者、等价输出测试”的顺序整理；不可全站删除旧插件或把兼容清理与报价预约逻辑升级捆绑上线。
- 需要读取 Search Console 才能确认收录、点击率、查询词、真实 Core Web Vitals；本次不提供虚构 SEO 分数、排名提升幅度或加载达标结论。

## 推荐执行顺序

1. 本轮：六套展示，先备份，再上线，完成真实浏览器回归。
2. 下一轮：优先核实并统一详情摘要的销售面积显示来源，不动报价单与预约；页脚色彩/布局先离线预览。
3. 然后只处理 sitemap 的真实更新信号，风险较小。
4. 之后单独做视频/图片性能预览和前后对比，逐页减负。
5. 再做独立施工观看页与关键词内容；确有中文搜索需求后再开发 `/zh/`。

每批均独立备份、独立验收、只回退自己拥有的源文件；不恢复客户数据库，不改变报价单、预约接口、广告预算或公开优惠政策。本报告是公开页面和静态输出检查，不是法律审查、安全渗透测试、全部交互认证或真实设备性能认证。
